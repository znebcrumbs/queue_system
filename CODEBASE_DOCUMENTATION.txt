1) Project overview
-------------------
Name: queue_system
Framework: Django (project created with Django 5.x)
Database: Postgres (configured in `config/settings.py`) — local dev can use Postgres or adjust to SQLite.

High-level apps:
- `q_accounts`: custom user model + auth-related views/admin customizations.
- `q_queues`: core queueing logic (departments, service types, queue entries), views, templates.
- `q_survey`: survey models and views (feedback/rating on served queues).
- `config`: Django project settings, URLs, WSGI/ASGI.
- `rest_framework`: Django REST Framework for API endpoints.

The project uses a custom `AUTH_USER_MODEL` defined at `q_accounts.models.User` (subclass of `AbstractUser`).
The project uses `python-decouple` for environment variable configuration management.


2) Setup & run
---------------
Prerequisites:
- Python 3.10+ (project uses 3.10+ in examples; adjust for your environment)
- PostgreSQL (or adapt DATABASES to sqlite3 for quick dev)
- virtualenv or venv recommended
- Additional dependencies listed in `requirements.txt`: qrcode, channels, python-dotenv, djangorestframework, psycopg2-binary

Quick start (development):

Windows PowerShell example (from project root):
```powershell
# Bypass script execution policy (Windows only, if needed)
Set-ExecutionPolicy -ExecutionPolicy RemoteSigned -Scope CurrentUser

# Create virtual environment using virtualenv
python -m virtualenv venv

# Activate virtual environment (Windows PowerShell)
.\venv\Scripts\Activate

# Install all dependencies from requirements.txt
pip install -r requirements.txt

# Update DB settings in `config/settings.py` if needed, then run migrations
python manage.py migrate

# Create superuser for admin access
python manage.py createsuperuser

# Run the development server
python manage.py runserver
```

Notes:
- For production, set `DEBUG=False`, configure `ALLOWED_HOSTS`, secure cookie flags and HTTPS.
- There are commands in the doc for backing up Postgres (`pg_dump`) and creating users non-interactively.


3) Apps and responsibilities
-----------------------------
q_accounts
- Location: `q_accounts/`
- Contains `models.py` with `User(AbstractUser)` augmented with `role` (TextChoices) and `department` FK.
- `admin.py` registers a `CustomUserAdmin` that exposes `role` and `department` in admin.
- `views.py` includes `CentralLoginView` (subclass of `LoginView`) that sets `get_success_url` depending on user role.

q_queues
- Location: `q_queues/`
- Models: `ServiceType`, `Department`, `QueueEntry`.
- Views: `dashboard`, `queue_list` (AJAX), `create_queue_entry` (csrf_exempt for kiosks), `update_queue_entry` (status updates), `kiosk`, `generate_qr`, `reports_dashboard`, CSV exports, `department_selection`.
- Templates: `templates/q_queues/*`, partials under `templates/q_queues/partials` including `queue_table.html`.
- Admin: `q_queues/admin.py` registers `ServiceType`, `QueueEntry`, `Department`.

q_survey
- Location: `q_survey/`
- Contains survey models and basic views (used in reports). See `q_survey/models.py`.


4) Models summary
------------------
Key models (fields summarized):

- `q_accounts.models.User` (extends `AbstractUser`)
  - `department` -> FK to `q_queues.Department` (nullable)
  - `role` -> CharField with choices: ADMIN, REGISTRAR, MIS (default: MIS)

- `q_queues.models.Department`:
  - `name` (unique), `description`, `slug` (unique, auto-generated from name)
  - `max_entries_per_day` (PositiveIntegerField, default=0 for unlimited) — enforcement at queue entry creation

- `q_queues.models.ServiceType`:
  - `name`, `description`, `prefix`, `department` (FK), `assigned_role`
  - `generate_queue_number()` helper to generate queue numbers

- `q_queues.models.QueueEntry`:
  - `client` (FK to User, nullable), `service_type` (FK), `queue_number` (CharField, no unique constraint)
  - `qr_code_data` (TextField, UUID-based), `status` (TextChoices: WAITING, SERVED, RETURNED, CANCELLED)
  - `created_at`, `served_at`, `created_date` (DateField auto-generated), `department` (FK, nullable)
  - `name`, `mobile_number`, `email`, `section` fields for customer info
  - UniqueConstraint for queue_number/service_type/created_at (per-day uniqueness)


5) Views & URLs (high-level)
-----------------------------
Important views and behavior:

- Authentication:
  - `q_accounts.views.CentralLoginView` (LoginView subclass) — route `q_accounts/urls.py` defines `login/` to this view.
  - `LOGIN_URL`, `LOGIN_REDIRECT_URL`, `LOGOUT_REDIRECT_URL` set in `config/settings.py`.

- Dashboard & Queue
  - `q_queues.views.dashboard`: Staff/Admin dashboard. If staff user has no `department` the view redirects to `department_selection` (avoid login redirect loop).
  - `q_queues.views.queue_list`: AJAX endpoint returning HTML partial and metadata for current queue + served entries.
  - `q_queues.views.create_queue_entry`: `@csrf_exempt` endpoint for kiosk devices to create a new queue entry.
  - Decorated with `@api_key_required` and `@throttle_kiosk` for security and rate limiting.
  - Enforces per-department daily capacity limits (`max_entries_per_day`).
  - API key validation via `X-KIOSK-API-KEY` header, POST param, or GET param.
  - Rate limit: 10 requests per minute per IP address.
  - Returns JSON with entry details including queue number and QR code data.
  - `q_queues.views.update_queue_entry`: endpoint (POST or GET, `@csrf_exempt`) to update `QueueEntry` status.
  - Accepts both authenticated staff users and API-key authenticated kiosk devices.
  - Falls back to API key authentication if user is not authenticated.
  - Enforces HTTP method restrictions (POST/GET only).
  - `q_queues.views.kiosk`: public-facing kiosk UI to create tickets.
  - `generate_qr`, `queue_ticket` to display ticket QR and ticket page.

- Reports & CSV
  - `reports_dashboard`, `export_queues_csv`, `export_surveys_csv` — staff-facing reports and CSV export utilities.

Routes are defined in each app's `urls.py` and included centrally in `config/urls.py`.


6) Templates & front-end behavior
---------------------------------
Main templates:
- `templates/accounts/login.html` — staff login (contains `{% csrf_token %}`).
- `templates/q_queues/dashboard.html` — main staff dashboard with Now Serving, Next in Queue, Active Queue List. The file contains JavaScript that:
  - Polls `/queues/queue_list` every 5 seconds (AJAX) and replaces the `#queue-table` HTML partial
  - Plays a sound and highlights the queue number when "   ,  " changes
  - Implements a confirmation modal for actions (Call Next, Serve/Return/Cancel) using Bootstrap 5 modal API
  - The `Call Next` button shows confirmation modal, then sends POST to `/queues/update/<id>/` and refreshes queue

- `templates/q_queues/partials/queue_table.html` — table partial used by the AJAX call. Forms in this partial have class `confirm-form`; the dashboard JavaScript intercepts their submit and shows the modal before performing AJAX POST.

Front-end notes:
- The project uses jQuery for AJAX and DOM handling and Bootstrap 5 for styles & modal. The code uses the Bootstrap 5 Modal JS API (not jQuery `.modal()`) to avoid compatibility issues.
- Audio playback is attempted via `audio.play().catch()` to avoid unhandled promise rejections when autoplay is blocked.


7) Admin configuration
----------------------
- `q_accounts/admin.py` registers `User` with a `CustomUserAdmin` that exposes `role` and `department` fields and enables filtering/search.
- `q_queues/admin.py` registers `ServiceType`, `QueueEntry`, and `Department` for admin management (create/edit departments and service types; see admin to assign `assigned_role`).

Admin actions to manage departments and users:
- Create Departments in admin (q_queues → Departments).
- Assign `department` to users via the User admin to avoid redirect loops on the dashboard.


8) Security / Cookies / CSRF notes
----------------------------------
- `AUTH_USER_MODEL` is `q_accounts.User` in `config/settings.py`.
- Cookie settings in `config/settings.py` (sensible dev defaults present):
  - `CSRF_COOKIE_SECURE = False`
  - `SESSION_COOKIE_SECURE = False`
  - For production, set both to True and use HTTPS.
- Middleware includes `SessionMiddleware`, `CsrfViewMiddleware`, `AuthenticationMiddleware` in the correct order.
- **Kiosk protection:**
  - Kiosk endpoints (`create_queue_entry`, `update_queue_entry`) are `@csrf_exempt` because kiosk devices may not handle CSRF tokens.
  - All kiosk endpoints require API key authentication via `@api_key_required` decorator.
  - API key is configured via environment variable `KIOSK_API_KEY`.
  - Rate throttling is enforced: 10 requests per minute per IP address via `@throttle_kiosk` decorator.
  - Unauthorized attempts are logged with IP address for monitoring.


9) Known issues & fixes applied
--------------------------------
- Redirect loop after login: If a staff user had no `department`, the dashboard used to redirect to `login`, creating a loop. Fix: dashboard now redirects to `department_selection` (and `CentralLoginView.get_success_url` can route to a safe page). Also better to render a `no_department` message or redirect to profile.
- Duplicate modal / redeclared JS variable error: The confirmation modal & JS were duplicated inside the partial `queue_table.html`. Fix: keep a single modal and handlers in `dashboard.html` and remove the inline script/modal from the partial. This prevented `Identifier 'formToSubmit' has already been declared` and other errors.
- Bootstrap modal API: The project uses Bootstrap 5 which removed jQuery plugins. Calls were updated to use the Bootstrap 5 JS API (`new bootstrap.Modal(...)`) and removed reliance on `$(...).modal()`.
- Session & CSRF troubleshooting notes: There are commands and server-side checks to confirm session creation (look up `django.contrib.sessions.models.Session`) and to check whether the `_auth_user_id` key is present in session data.
- Missing objects on other machines: calling `.get()` without handling `DoesNotExist` can crash scripts. Use `.filter().first()`, `get_or_create`, or try/except to make scripts robust.


10) Logging & Monitoring
-----------------------
- Comprehensive logging is configured in `config/settings/base.py`.
- Log format: `{levelname} {asctime} {module} {message}`
- Logs are written to `queue_system.log` file and streamed to console.
- Queue operations (`apps.queues`) logged at INFO level, including:
  - New queue entries created
  - Capacity reached warnings
  - Unauthorized access attempts
  - Exception stack traces
- Use log files to audit queue activity and debug production issues.

13) Environment Configuration
-----------------------------
The application uses `python-decouple` for environment variable management. Configure these in a `.env` file:
- `SECRET_KEY` — Django secret key (defaults to insecure value for dev)
- `DEBUG` — set to False for production
- `ALLOWED_HOSTS` — comma-separated list (defaults to 'localhost,127.0.0.1')
- `KIOSK_API_KEY` — API key for kiosk device authentication (required)
- `DATABASES` — if using environment-based DB config

Example `.env`:
```
DEBUG=False
SECRET_KEY=your-secure-key-here
ALLOWED_HOSTS=example.com,www.example.com
KIOSK_API_KEY=your-secure-api-key-here
```
